================================================================================
 DMS / doc_engine1  -  OCR ENGINE DEPLOYMENT GUIDE (GPU SERVER)
================================================================================
 Goal : run the OCR backend + HTML frontend on a Linux GPU server, reachable
        over an API, producing output IDENTICAL to the local Windows machine.

 Written : 2026-08-07
 Source of truth : versions below were read from the LOCAL venv
                   (ocr/venv/Lib/site-packages), not from requirements.txt.
================================================================================


================================================================================
 0. WHAT YOU ARE DEPLOYING
================================================================================

Three moving parts:

  1. FastAPI backend            ocr/main.py                 port 8000
  2. Static HTML frontend       ocr/index.html + app.js     port 8080 (to merge)
  3. Ollama + vision model      AuditAid/PaddleOCR-VL-1.6-0.9B   port 11434

Pipeline (the "aligned" engine, ocr/aligned_pipeline.py):
  load page -> detect page region -> deskew -> detect text line boxes
  -> recognise each line via PaddleOCR-VL over Ollama HTTP
  -> Telugu->Kannada codepoint shift (+0x80)
  -> inpaint original text away -> redraw recognised text at same position
  -> emit clean_bg.png, overlay.png, aligned.docx, lines.json

The legacy engine (Tesseract via ocrmypdf) still exists at engine="legacy".
The searchable-PDF download (/download/{job_id}) ALWAYS uses ocrmypdf+Tesseract,
so Tesseract is required even if you only ever use the aligned engine.

NOTE: There is NO PaddlePaddle / paddleocr / torch dependency. The model is
reached purely over HTTP to Ollama. "Paddle" is only the model's lineage.

 1. SERVER PREREQUISITES
================================================================================

  OS          Ubuntu 22.04 or 24.04 LTS
  Python      3.12.x   (local venv is 3.12.10 - match the minor version)
  GPU         Any CUDA GPU. The model is only 0.9B params (~1 GB VRAM),
              so even a T4 / 8 GB card is plenty. GPU is for speed, not size.
  Disk        20 GB+ . Each OCR job writes input + preprocessed + pdf + docx
              into ocr/ocr_workspace/<job_id>/ and NOTHING deletes them.
  RAM         8 GB+
  Driver      NVIDIA driver + CUDA runtime installed and `nvidia-smi` working
              BEFORE installing Ollama, or Ollama silently falls back to CPU.

 5. OLLAMA + GPU (the recognition model)

    curl -fsSL https://ollama.com/install.sh | sh

    ollama pull AuditAid/PaddleOCR-VL-1.6-0.9B

    ollama run AuditAid/PaddleOCR-VL-1.6-0.9B "hi"    # warm it up
    ollama ps
    # The PROCESSOR column must say 100% GPU. If it says CPU, fix your
    # NVIDIA driver first - CPU inference is ~20x slower here.

Tune the Ollama service. Edit with `sudo systemctl edit ollama.service`:

    [Service]
    Environment="OLLAMA_KEEP_ALIVE=-1"
    Environment="OLLAMA_NUM_PARALLEL=4"
    Environment="OLLAMA_HOST=127.0.0.1:11434"

  OLLAMA_KEEP_ALIVE=-1   keeps the model resident. Default unloads after 5 min,
                         so the first request after idle pays a reload.
  OLLAMA_NUM_PARALLEL=4  without this Ollama serialises requests and the
                         backend's OCR_WORKERS=3 buys you nothing.
  OLLAMA_HOST 127.0.0.1  keep Ollama private; only the backend should reach it.

Then:
    sudo systemctl daemon-reload && sudo systemctl restart ollama

DETERMINISM NOTE:
  The code already sends temperature=0 and num_predict=512
  (aligned_pipeline.py:539), so sampling is greedy. But GPU kernels can still
  produce slightly different tokens than your local CPU run. Because font size
  is fitted TO THE RECOGNISED STRING, a different string can shift font_px.
  To reproduce your local results exactly on known pages, copy the cache:
      scp ocr/ocr_workspace/.ocr_cache.json server:/opt/dms_engine/doc_engine1/ocr/ocr_workspace/
  The cache is keyed on crop-bytes + model-name, so it transfers cleanly.


================================================================================
 6. *** FONTS - THIS IS WHAT BREAKS "SAME AS LOCAL" ***
================================================================================

THE PROBLEM
-----------
aligned_pipeline.py:30 lists font candidates in priority order:

    FONT_CANDIDATES = [
        r"C:\Windows\Fonts\Nirmala.ttc",                    <- you get this locally
        "/usr/share/fonts/truetype/noto/NotoSansKannada-Regular.ttf",  <- server
        "/usr/share/fonts/truetype/lohit-kannada/Lohit-Kannada.ttf",
    ]

pick_font() returns the FIRST path that exists. Nirmala.ttc does not exist on
Linux, so the server loads a DIFFERENT font than your PC.

That changes your output, because font size is MEASURED, not assumed:
  assign_font_sizes() shrinks the size until dr.textbbox() fits the detected
  box (aligned_pipeline.py:936-973). Different font file
    -> different glyph advance widths
    -> different chosen font_px
    -> different overlay.png AND different w:sz in the .docx

Bold also breaks silently: Fitter.font() hardcodes
  C:\Windows\Fonts\NirmalaB.ttf (aligned_pipeline.py:869), which is absent on
  Linux, so every bold line falls back to regular weight.

And write_docx() hardcodes the font NAME "Nirmala UI"
  (aligned_pipeline.py:1167) regardless of which file was actually measured.

WARNING: ocr/NotoSansKannada.zip in this repo IS NOT A ZIP FILE.
  I checked the magic bytes - it starts with "<!doctype html>". It is a saved
  error page from a failed download. Do not try to use it.

THE FIX - vendor the font so both machines load the SAME FILE
-------------------------------------------------------------
Step 1. Make the folder and copy the fonts from your Windows PC.

  On Windows (cmd, from doc_engine1\):
    mkdir ocr\fonts
    copy C:\Windows\Fonts\Nirmala.ttc   ocr\fonts\
    copy C:\Windows\Fonts\NirmalaB.ttf  ocr\fonts\

  Get them onto the server - EITHER commit them (preferred, they then ship
  with every deploy):
    git add -f ocr/fonts/Nirmala.ttc ocr/fonts/NirmalaB.ttf
    git commit -m "vendor Kannada fonts so all hosts measure text identically"
    #  -f is needed because section 13's .gitignore excludes *.zip/*.exe and
    #  you may have broadened it; fonts must NOT stay ignored.

  OR copy them up directly (from Windows PowerShell / Git Bash):
    scp ocr/fonts/Nirmala.ttc ocr/fonts/NirmalaB.ttf \
        user@server:/opt/dms_engine/doc_engine1/ocr/fonts/

  On the server, verify they landed and are readable by the service user:
    ls -l /opt/dms_engine/doc_engine1/ocr/fonts/
    sudo chown -R www-data:www-data /opt/dms_engine/doc_engine1/ocr/fonts

Step 2. Edit ocr/aligned_pipeline.py, replace lines 29-34 with:

    FONT_DIR = os.environ.get("OCR_FONT_DIR", os.path.join(HERE_DIR, "fonts"))

    # Vendored fonts FIRST: text metrics - and therefore font_px and the DOCX
    # w:sz - depend on the exact file, so every host must load the same one or
    # output drifts between machines.
    FONT_CANDIDATES = [
        os.path.join(FONT_DIR, "Nirmala.ttc"),
        r"C:\Windows\Fonts\Nirmala.ttc",
        os.path.join(FONT_DIR, "NotoSansKannada-Regular.ttf"),
        "/usr/share/fonts/truetype/noto/NotoSansKannada-Regular.ttf",
        "/usr/share/fonts/truetype/lohit-kannada/Lohit-Kannada.ttf",
    ]
    BOLD_CANDIDATES = [
        os.path.join(FONT_DIR, "NirmalaB.ttf"),
        r"C:\Windows\Fonts\NirmalaB.ttf",
        os.path.join(FONT_DIR, "NotoSansKannada-Bold.ttf"),
    ]

Step 3. In Fitter.font() (around line 869), replace the hardcoded Windows
        tuple with the list above:

        for cand in BOLD_CANDIDATES + [self.path]:
            if os.path.exists(cand):
                for idx in (1, 0):
                    try:
                        loaded = ImageFont.truetype(cand, px_i, index=idx)
                        break
                    except Exception:

            if loaded:

Step 4. Make the DOCX name the font you actually measured with. Near line 1167:

    DOCX_KN_FONT = os.environ.get("OCR_DOCX_FONT", "Nirmala UI")
    ...
    name = DOCX_KN_FONT if kn else "Arial"

LICENSING - READ THIS
---------------------
Nirmala UI is a Microsoft font bundled with Windows. Copying it to a Linux
server is a licensing question you need to confirm for your situation.
Two clean choices:

  OPTION A (output stays byte-identical to your current local output):
      copy Nirmala.ttc + NirmalaB.ttf into ocr/fonts/ as above.
      Keep OCR_DOCX_FONT="Nirmala UI".
      Your Windows Word users already have the font, so the .docx renders right.

  OPTION B (licence-clean, reproducible anywhere):
      Download Noto Sans Kannada (SIL Open Font License) from
        https://fonts.google.com/noto/specimen/Noto+Sans+Kannada
      Put NotoSansKannada-Regular.ttf + -Bold.ttf into ocr/fonts/
      Put them FIRST in FONT_CANDIDATES and set OCR_DOCX_FONT="Noto Sans Kannada"
      USE THE SAME FILES LOCALLY TOO.
      Your output shifts once (different metrics), then local == server forever.
      Caveat: Word users need the font installed or Word substitutes it.

Either way the rule is the same:
  >>> ONE font file, used on BOTH machines. <<<

--- 7a. FIX THE CRASH  (ocr/main.py line 504) --------------------------------
normalise() returns 6 values; this unpacks 4. Every "edit text then download
DOCX" request returns a 500 right now.

  BEFORE:  rot, ink, _, _ = normalise(img)
  AFTER:   rot, ink, _, _, _, _ = normalise(img)


--- 7b. SERVE THE HTML FROM FASTAPI (one port, no CORS) ----------------------
Right now app.js has a hardcoded 'http://localhost:8000'. That only works if
the browser is on the SAME machine as the API - a remote user's browser
resolves localhost to their own PC and gets connection refused.

In ocr/main.py, AFTER all @app route definitions (must be last, or the mount
shadows your API routes), add:

    from fastapi.staticfiles import StaticFiles
    app.mount("/", StaticFiles(
        directory=os.path.dirname(os.path.abspath(__file__)),
        html=True), name="ui")

In ocr/app.js line 13:
    BEFORE:  apiBaseUrl: 'http://localhost:8000',
    AFTER:   apiBaseUrl: '',        // same origin

Result: everything on port 8000. ocr/serve_frontend.py is no longer needed
(it was a dev-only stdlib server anyway).


--- 7c. LOCK DOWN CORS  (ocr/main.py line 39-45) -----------------------------
Currently allow_origins=["*"] WITH allow_credentials=True - an invalid
combination that browsers reject, and wide open. After 7b you barely need CORS:

    _origins = [o for o in os.environ.get("CORS_ORIGINS", "").split(",") if o]
    app.add_middleware(
        CORSMiddleware,
        allow_origins=_origins,       # empty = same-origin only
        allow_credentials=False,
        allow_methods=["GET", "POST"],
        allow_headers=["*"],
    )


--- 7d. DO NOT BLOCK THE EVENT LOOP  (ocr/main.py) ---------------------------
process_page and run_ocrmypdf are heavy blocking calls (ocrmypdf alone is
~140s) sitting inside `async def`. One upload freezes EVERY other client.
This is survivable locally with one user; it is not on a shared server.

At the top of main.py:
    from starlette.concurrency import run_in_threadpool

In /extract (line ~392) and /formatted (line ~527):
    BEFORE:  r = process_page(input_path, job_dir, want_docx=True)
    AFTER:   r = await run_in_threadpool(process_page, input_path, job_dir,
                                        want_docx=True)

In /download (line ~564) and /extract/raw (line ~356):
    BEFORE:  run_ocrmypdf(src, job_id)
    AFTER:   await run_in_threadpool(run_ocrmypdf, src, job_id)


--- 7e. MAKE THE OCR CACHE THREAD-SAFE  (ocr/aligned_pipeline.py) ------------
cache_init() rebinds the global _CACHE on EVERY request (line 517) while
another request's worker threads are writing to it (line 544, no lock), and
cache_save() rewrites the whole file. Two concurrent uploads lose each other's
entries, and json.dump can raise
"RuntimeError: dictionary changed size during iteration".

Add near the top:
    import threading
    _CACHE_LOCK = threading.Lock()
    _CACHE_LOADED = False

cache_init - load once, not per request:
    def cache_init(outdir):
        global _CACHE_PATH, _CACHE, _CACHE_LOADED
        with _CACHE_LOCK:
            if _CACHE_LOADED:
                return
            shared = os.environ.get("OCR_CACHE_DIR") or os.path.join(HERE_DIR, "ocr_workspace")
            try:
                os.makedirs(shared, exist_ok=True)
                _CACHE_PATH = os.path.join(shared, ".ocr_cache.json")
            except Exception:
                _CACHE_PATH = os.path.join(outdir, ".ocr_cache.json")
            if os.path.exists(_CACHE_PATH):
                try:
                    with open(_CACHE_PATH, encoding="utf-8") as f:
                        _CACHE = json.load(f)
                    print(f"ocr cache: {len(_CACHE)} entries")
                except Exception:
                    _CACHE = {}
            _CACHE_LOADED = True

cache_save - snapshot under lock, write atomically:
    def cache_save():
        if not _CACHE_PATH:
            return
        with _CACHE_LOCK:
            snap = dict(_CACHE)
        tmp = _CACHE_PATH + ".tmp"
        with open(tmp, "w", encoding="utf-8") as f:
            json.dump(snap, f, ensure_ascii=False)
        os.replace(tmp, _CACHE_PATH)

recognise() - guard both read and write:
        with _CACHE_LOCK:
            if key in _CACHE:
                return _CACHE[key]
        ... existing HTTP call ...
        with _CACHE_LOCK:
            _CACHE[key] = out
        return out

 11b. FIREWALL / CLOUD SECURITY GROUP  (the usual "why can't I connect")
================================================================================

TWO layers can block you. Both must allow the port.

Layer 1 - the OS firewall (ufw):
    sudo ufw status
    # if active:
    sudo ufw allow 22/tcp          # keep SSH open or you lock yourself out
    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp
    # ONLY if you skipped nginx and expose uvicorn directly:
    sudo ufw allow 8000/tcp
    sudo ufw reload

Layer 2 - your cloud provider's security group / network rules. This is
separate from ufw and is the more common culprit. Open the same ports in:
    AWS      EC2 > Security Groups > Inbound rules
    GCP      VPC network > Firewall
    Azure    Network security group > Inbound security rules
    RunPod / Vast.ai / Lambda  -> "expose HTTP port" in the pod config

NEVER expose these:
    11434   Ollama - no auth at all, anyone could run inference on your GPU.
            Keep OLLAMA_HOST=127.0.0.1 (section 5).
    8000    if nginx is in front. Bind uvicorn to 127.0.0.1 (section 10) so it
            is unreachable from outside except through the proxy.

Confirm what is actually listening and on which interface:
    sudo ss -tlnp | grep -E "8000|11434|:80|:443"
    # 127.0.0.1:8000  = local only (correct when behind nginx)
    # 0.0.0.0:8000    = exposed to the internet (only OK if that is intended
    #                   AND OCR_API_KEY is set - see section 7g)

Test from your own machine, not from the server:
    curl -sS http://<server-ip>/health        # via nginx
    curl -sS http://<server-ip>:8000/health   # direct, if you skipped nginx

.gitignore in doc_engine1/ is saved as UTF-16LE with a BOM, so git cannot

Fix on your Windows machine BEFORE deploying:
